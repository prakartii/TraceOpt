1. The idea in plain words

A zero-knowledge virtual machine (zkVM) such as RISC Zero runs a program and produces a proof that it ran correctly. Anyone can check the proof quickly without re-running the program. Producing the proof is the expensive part, and its cost grows with the number of execution steps (cycles).

RISC Zero proves cycles in blocks whose size is a power of two: a run that needs 140,000 cycles is proved as 262,144. Saving cycles therefore only lowers the proving cost when the run drops into a smaller power-of-two size. Ordinary compilers optimize for CPU speed and know nothing about this.

TraceOpt generates several versions of a program (here: loop unrolling), predicts the proving size of each one without running the zkVM, and chooses the cheapest version it can trust. The zkVM then runs the chosen version so the prediction can be checked against the real numbers.

2. Example: strided_rw with n = 5

A memory-heavy kernel just above a power-of-two boundary.

The program (benchmarks/strided_rw.c)

// Memory-intensive kernel: fills a 64 KiB static array, then performs n
// passes of strided read-modify-write (1 KiB stride, 64 accesses per pass).
// Intended to touch many distinct memory pages in the zkVM.
#include <stdint.h>

#define WORDS 16384u /* 64 KiB of uint32_t */
#define STRIDE 256u  /* 1 KiB */

static uint32_t buf[WORDS];

uint32_t traceopt_kernel(uint32_t n) {
  for (uint32_t i = 0; i < WORDS; i++) {
    buf[i] = i * 2654435761u;
  }
  uint32_t acc = 0;
  for (uint32_t r = 0; r < n; r++) {
    for (uint32_t i = 0; i < WORDS; i += STRIDE) {
      uint32_t k = (i + r) & (WORDS - 1);
      acc = (acc ^ buf[k]) + r;
      buf[k] = acc;
    }
  }
  return acc;
}

Decision

A version is chosen only if it lowers the proved size by at least 5%, still does so when its prediction is 10% too optimistic, passed the answer checks, and grows the code by at most 16×.

3. Example: xorshift with n = 1000

Unrolling saves cycles, but whether it saves proving work is uncertain.

The program (benchmarks/xorshift.c)

// Simple loop with a loop-carried dependence: n rounds of xorshift32.
// Unlike sum_squares, LLVM cannot replace this loop with a closed form,
// so its cycle count scales with n.
#include <stdint.h>

uint32_t traceopt_kernel(uint32_t n) {
  uint32_t x = 2463534242u;
  for (uint32_t i = 0; i < n; i++) {
    x ^= x << 13;
    x ^= x >> 17;
    x ^= x << 5;
  }
  return x;
}

5. What this shows, and its limits

  • Proving cost moves in power-of-two steps, so most cycle savings do not change it. An optimizer needs to know where the steps are.
  • TraceOpt predicts cycles from LLVM IR without running the zkVM and uses the prediction to decide; when it changed the code, the predicted saving was real.
  • It is deliberately cautious near the step edges: that avoided false wins and also missed some real ones.

Limits: four small kernels; one optimization (loop unrolling); cycle counts from RISC Zero's executor (full proofs did not fit in the development machine's memory); answers checked on test inputs, which is not a formal proof of equivalence.
